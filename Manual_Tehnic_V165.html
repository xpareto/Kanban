1. Arhitectură generală

ProjectBoard este o aplicație single-file HTML/JS/CSS fără dependențe externe (cu excepția Firebase CDN și Google Calendar REST API). Rulează ca PWA instalată din Chrome pe Android. Iconița de pe ecranul de start și tab-ul de Chrome partajează același localStorage (același origin) — nu sunt stocări separate.

FreeTask

{
  id: string,           // 'id_' + random, sau 'cal::'+googleEventId
  name: string,         // Textul taskului (prima linie) + URL-uri (linii 2+)
  note?: string,        // Notă privată
  subtasks?: SubtaskEntry[], // Dy1 (V159): listă ierarhică de subtaskuri
  ts: number,           // Timestamp creare
  modifiedTs: number,   // Timestamp ultima modificare conținut
  zone: 'green'|'red'|'yellow'|null,  // Zona de culoare în NEXT — sursa pentru T1/Split-View
  zoneRank: number,     // Poziția în cadrul zonei (0-based)
  zoneMts: number,      // Timestamp ultima modificare zonă (independent de modifiedTs)
  isCalEv?: true,       // marchează un rând adus din Google Calendar
  calStart?: string,    // ISO — start-ul evenimentului (pentru extractDateFromRow)
  _deleted?: true       // Tombstone pentru sync ștergere
}

4. Sistemul de zone colorate

Zonele sunt delimitate de perechi de marcatori (free tasks al căror name începe cu *1, *2, sau *3).

ZonăMarcatoriCuloareRol
Verde*3…*3#DCFCE7Prioritate absolută aleasă manual — coloana stângă din Split-View
Roșie*1…*1#FEE2E2Tasks cu termene — sortate cronologic — parte din coloana dreaptă din Split-View
Galbenă*2…*2#FEF9C3Priorități secundare — parte din categoria „Restul" (T1)

detectAndSaveZones()

Parcurge S.nextOrder direct (nu getNR). Calculează zone și zoneRank pentru fiecare item. Marcatorii *1/*2/*3 primesc întotdeauna zone=null. Cal:: events sunt skipped. La fiecare schimbare: zoneMts=Date.now(), modifiedTs=max(modifiedTs+1, now). Salvează FK și SK.

Regulă critică (R12, întărită în V154): detectAndSaveZones() trebuie apelată după orice operație care schimbă nextOrder — inclusiv cele trei funcții de sortare globală (sortBetweenMarkers, sortRestNext, sortByTime), care în V139–V153 nu o apelau. Bug găsit: view-ul clasic colorează benzile pe bază de poziție la render, deci bug-ul era invizibil acolo — dar T1 (taburi) și Split-View citesc câmpul zone stocat pe obiect, nu poziția. Un task nou, sortat corect în nextOrder dar cu zone=null nestocat, apărea corect ca roșu în view-ul clasic dar în „Restul" în Split-View. Fixat V154 — toate cele trei funcții de sortare apelează acum detectAndSaveZones() înainte de save().

6. Sincronizare Firebase

Push (fbPush)

Apelează detectAndSaveZones() înainte de payload. Trimite tombstones din pb-deleted-ids ca FreeTask-uri cu _deleted:true. Refuză push cu date demo.

G1 — Guard scădere semnificativă (V145, incident real de pierdere date pe tabletă): înainte de push, compară dataSize(S.items,S.freeTasks) (proiecte+taskuri+free tasks reale, exclus marcatori/cal::) cu pb-last-good-size. Dacă scăderea e ≥10% (SIZE_GUARD_PCT), afișează un modal de confirmare (confirmSizeGuard) înainte de a scrie în Firestore — utilizatorul poate anula, continua oricum, Merge (V155, G4 — uniune completă, vezi mai jos), sau (doar la Push) comuta direct pe Pull (recomandat, buton verde). Funcționează identic la push manual, automat (la lansare) și din fbSync().
G3 — Diferență pe categorii (V148): quando guard-ul se declanșează, diffTaskSets() compară local vs remote pe categorii — NEXT (🟢 Prioritare / 🔴 Termene / 📅 Calendar / ⚪ Restul), ⏳ WAIT, 📥 SHARE — nu doar un total brut. Modalul arată sumar compact „local +X / cloud +Y" per categorie, plus lista de nume (max 10/categorie) doar acolo unde există diferență reală. La Push, fetch-ul de date remote (pentru diff) se face doar dacă guard-ul chiar se declanșează — push-ul normal rămâne rapid, fără citire suplimentară.
G4 — Merge din modalul de guard (V155): al treilea buton, disponibil și la Push și la Pull — face uniune completă (fbPull('merge')), apoi, la Push, scrie direct cu _doActualPush(), funcția de scriere Firestore extrasă din fbPush() ca să nu re-declanșeze propriul ei guard imediat după merge. La Pull, alegerea „merge" din guard-ul de overwrite re-intră direct în fbPull('merge') (recursiv, schimbă mode-ul — fără risc de buclă, fiindcă mode==='merge' nu mai are guard propriu).

7. Google Calendar

Flux autentificare

La prima lansare din zi:
1. Silent re-auth (prompt:none) → dacă eșuează (interaction_required)
2. Login explicit (prompt:select_account)
3. OAuth OK → fetch calendarList → fetchCal pentru fiecare calendar
4. Filtrare events → calInjectEvents → showMorningModal

Filtrare events

Tip eventCondiție includere
All-day (start.date)evStart ≤ tomorrowF AND evEnd > todayF (end exclusivă: evEnd <= todayF = exclude)
Timed (start.dateTime)evStart ≤ tomorrowF AND evEnd < todayF = exclude (strict)

K1/K2 — Persistență evenimente calendar până la bifare (V140, extins V148)

K1. La fiecare calInjectEvents(events), rândurile cal:: vechi care NU mai apar în fetch-ul curent ȘI NU sunt în pb-deleted-ids (nebifate) sunt păstrate, cu label prefixat ↺ (o singură dată) — rămân vizibile în NEXT până sunt bifate manual. V148 fix: rândurile cal:: cu nume gol/corupt (rămase din bug-uri vechi) NU mai sunt păstrate — plus curățenie silențioasă la init() pentru cele deja acumulate.
K2. Evenimentele al căror id (cal::<eventId>) e deja în pb-deleted-ids (bifate via butonul ✓ verde din NEXT, care apelează delFree) sunt excluse din fetch-ul reconstruit — nu revin, chiar dacă Google Calendar le mai întoarce ca active (ex: eveniment pending pe mai multe zile, bifat înainte de final).

Wipe-ul necondiționat zilnic din calCheckAndFetch (care ștergea toate cal:: o dată pe zi) a fost eliminat — merge-ul inteligent din calInjectEvents preia acest rol. pb-cal-cleaned rămâne doar pentru resetarea zilnică a flag-urilor de silent-auth.

„Ziua X din N" — evenimente ongoing (V141, C1)

calDayOfN(ev) calculează, pentru un eveniment all-day multi-zi aflat în desfășurare, eticheta (ziua X din N) — ex: [ongoing 20-30 iul] Concediu (ziua 6 din 11). Returnează string gol pentru evenimente de o singură zi.

FINALIZARE persistent — pending intervals (V148, C2)

Problemă rezolvată: dacă utilizatorul șterge rândul sursă cu intervalul (ex: 26.7-26.8) imediat după creare (ca să nu aglomereze NEXT), reminder-ul FINALIZARE (cu 4 zile înainte de d2) nu se mai crea, fiindcă depindea de re-scanarea rândului sursă.

checkAndCreateFinalizare(name) acum salvează/actualizează un reminder persistent în pb-pending-final (via savePendingFinalizare) indiferent dacă a ajuns data de apariție — decuplat de existența rândului sursă. checkPendingFinalizari(), apelată la fiecare lansare (lângă applyWeekdaysToAll), reverifică toate intervalele pendinte și creează FINALIZARE la momentul potrivit, chiar dacă rândul original a fost șters între timp. Expirare hard: 30 zile după d2 (safety, evită acumulare infinită).

Sintaxă interval scurtat — zi.lună+N (V148, Î1)

resolvePlusInterval(text), integrată în resolveCalCmd (singurul punct de intrare, apelat la toate cele 9 puncte de salvare) — transformă 26.7+31 în formatul canonic 26.7-26.8 (N = zile adăugate la data inițială, capete inclusive). Validare: ziua ≤31, luna ≤12, altfel textul rămâne neschimbat (evită interpretarea greșită a altor „+" din text — telefoane, procente). Tolerant la spații: 26.7+31, 26.7 +31, 26.7 + 31.

10b. Mecanisme noi V161–V165

Banda de taburi și pornire

Din V163 aplicația pornește pe tabul prioritare (nu Split-View). Tabul zona2 („Z2-utile") conține rândurile cu zone==='yellow' (getNextRowCategory); „Restul" mai conține doar rândurile fără zonă. Butonul „+ Next" de sub listă a fost eliminat (V163) — rămâne FAB-ul și „+ Waiting". Secțiunea Share randează doar primele S.shareLimit||20 rânduri (V162).

Prefixe u / w

Regex /^([wWuU])[ .]/ pe numele afișat. u → fundal roșu, text îngroșat; w → galben închis + copie Wait (R23). Ordinea vizuală în tabul Prioritare (u, w, rest) se face cu CSS order (_rg2Active); mânerul ⠿ e dezactivat cât timp e activă.

Subtaskuri: note, ordine, promovare, sincronizare

Detaliile contractelor sunt în R24 și R27. Extragerea: blocuri după etichetă /^\s*\S{1,8}\.\s+\S/, primul rând după un separator (/^\s*(\.|={2,}|-{3,})\s*$/) sau primul bloc dacă există vreun separator; blocurile cu prefix X\d* sunt sărite; subtaskurile noi merg sus/jos după comutatorul ⬆ Top al editorului de notă. Neterminate copiază în clipboard subtaskurile nebifate.

Editorul de notă (V165)

Overlay pe tot ecranul (100dvh, ajustat cu visualViewport pentru tastatură); fereastra de linkuri e mică (max-height:84px) și conține doar lista numerotată de URL-uri, recalculată la input. Variabila globală _noteOwner (funcție care returnează obiectul-proprietar) e setată de apelanți înainte de showNoteOverlay și consumată imediat; fără ea, butoanele de subtaskuri nu apar.

Memorie și backup

fbBackupLocal() nu mai include shareTasks; la pornire, backup-urile vechi sunt curățate o singură dată. Overlay-ul Memorie grupează cheile după prefix (pb-* = Kanban pe componente; restul pe prefix, ex. trident_*) și afișează și navigator.storage.estimate() (include cache-ul aplicației).

Taskuri noi din cloud (Tuns)

tunsPlace e apelată în fbPull('merge') (în locul mergeNextOrderWithZones, cu fallback) și în ramura overwrite (după construirea merged2). Exclude marcatori și cal::; ≤30 de taskuri; marchează id-urile în pb-new-ids. Vezi R25.
